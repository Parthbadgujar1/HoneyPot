# SentinelTrap (AICD-TIP) — Engineering Report

**Project:** Adaptive AI-Driven Cyber Deception and Threat Intelligence Platform
**Short name:** AICD-TIP / SentinelTrap
**Scope:** Isolated honeypot + telemetry pipeline + behavioural ML + anomaly detection +
risk scoring + attack timeline/graph + sequence prediction + explainability + adaptive
deception + SOC dashboard. Safe, local-only, offensive-free research prototype.

---

## 1. Executive summary

A full-stack research prototype was designed and implemented from a greenfield repository
(only the project specification existed). The backend, ML pipeline, adaptive deception
engine, experiments module, an automated test suite, and a React SOC dashboard were all
built and verified end-to-end. A simulated attacker drives the entire defensive workflow:
telemetry ingestion → feature extraction → behaviour classification → anomaly detection →
risk scoring → timeline + attack graph → next-stage prediction → adaptive deception →
analytics → dashboard. The final engineering deliverable below details every area.

---

## 2. What was present at the start

The repository contained only `Adaptive_AI_Cyber_Deception_Honeypot_Project.md` (the spec),
which defines the project concept and 10 system modules (honeypot, telemetry, data
processing, classification, anomaly detection, sequence prediction, risk scoring, timeline,
attack graph, adaptive deception) plus a SOC web dashboard requirement. No code, database,

### 3.2 ML pipeline

- **Features:** 19 numeric features per session (`FEATURE_NAMES`, version v1) across
  temporal, authentication, behavioural, and network dimensions.
- **Classification** (supervised): 7 behavioural stages. Trained on synthetic labelled
  sessions generated by the simulator + training pattern generator. Default `random_forest`.
- **Anomaly detection** (unsupervised): Isolation Forest scoring deviation and identifying
  contributing features.
- **Sequence prediction:** Markov model over compressed stage sequences; reports top-1,
  top-3 and MRR.
- **Explainability:** SHAP-proxy feature-importance contributions for the classification
  and risk decisions.
- **Risk engine:** `anomaly + behaviour + sequence + resource + persistence` → 0–100 score,
  severity LOW/MEDIUM/HIGH/CRITICAL. Weights configurable (`RISK_WEIGHTS`).

### 3.3 Analysis orchestrator

`POST /sessions/{id}/analyse` runs: feature extraction → classification → anomaly →
prediction → risk → timeline → attack graph → explanation → adaptive deception, and
persists all artifacts.

### 3.4 Frontend (React + TypeScript + Tailwind + Vite + Recharts)

Soci dashboard with 15 pages: Overview, Live Events (WebSocket), Event Log, Sessions,
Session Investigation (features, risk contributions, timeline, attack graph, prediction,
deception actions), Anomalies, Behaviours, Risk, Analytics (charts), Deception, Model
Registry (train/activate), Honeypot (status + simulate), Audit, System. Custom SVG attack
graph renderer fed by Cytoscape.js-format nodes/edges.

### 3.5 Experiments & evaluation

`ml/experiments/experiment_runner.py` compares three modes (baseline / AI-assisted /
adaptive) and writes JSON+CSV metrics (sessions, events per session, behavioural coverage,
unique patterns, session depth, high-risk, anomalies, predictions, adaptive actions).

### 3.6 Tests

`backend/tests/` — 32 pytest tests covering features, sessionization, risk engine,
deception policies, simulator reproducibility/safety, ML model smoke tests, security/JWT,
and API integration (auth, RBAC, simulation, honeypot status) against a dedicated test DB.

## 7. Honeypot integration

- **Abstract adapter** (`base.py`) for pluggable honeypots.
- **Cowrie adapter** (`cowrie.py`): reads Cowrie JSONL logs (read-only).
- **LocalSimulatedHoneypot** (`local.py`): in-process simulated adapter — used because a
  real Cowrie/Docker honeypot cannot run on this Windows host. The collector thread polls
  it and pushes normalized events to the WebSocket bus and the DB.
- **Simulator** (`simulator.py`): 6 controlled scenarios — `auth_attempts`, `discovery`,
  `resource_enumeration`, `decoy_access`, `multi_stage`, `benign` — with deterministic
  seeds and private/local source IPs only.

Production would swap the adapter factory to `cowrie` and point `HONEYPOT_COWRIE_JSONL` at
the live honeypot log path (see `docker-compose.yml`/`.env`).

## 8. Adaptive deception policies

Five predefined, safe, reversible policies: `policy_keep_baseline`,
`policy_enable_db_decoy`, `policy_expose_config_decoy`, `policy_enable_resource_decoy`,
`policy_change_decoy_content`. The rule engine selects a policy from classification /
anomaly / risk inputs, executes it against the shared `DecoyEnvironment` singleton (so all
requests see consistent state), records an audit entry + a `deception_actions` row, and
supports rollback. Evaluated against locally-observed behaviour only — never targets
external systems.

## 11. Security

- PBKDF2 password hashing (stdlib; no passlib/bcrypt). JWT (PyJWT, HS256) with expiry.
- RBAC role hierarchy (VIEWER < RESEARCHER < ANALYST < ADMIN) enforced per route.
- Global exception handler suppresses stack traces; CORS allow-list; basic security headers.
- Decoy data only; no real secrets; all adaptive actions and auth events audited.
- `.env` is not committed; `.env.example` documents required values (dev secret).

## 14. Limitations

- **Simulated attackers only** — no live Cowrie/container honeypot running on this host;
  the local adapter substitutes for demonstration. Real-world validation requires Linux +
  Cowrie/T-Pot in an isolated lab.
- **Synthetic training data** — models are trained on synthetic labelled sessions, so
  generalization to real traffic is unvalidated.
- **Feature-importance explanations** are a SHAP *proxy* (model-agnostic), not full SHAP.
- **Sequence predictor** is a Markov baseline (not LSTM/GRU/transformer). Deep sequence
  models, RL-adaptive policies, and public-dataset benchmarking are future work.
- **Risk weights** are experimentally selected and documented as such, not formally tuned.
- Schema is model-driven (`create_all`); Alembic migrations are not configured.
- Windows host: Docker daemon must be started to actually build images.
